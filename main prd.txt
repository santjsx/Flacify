# AUREL — Premium Offline Music Player
## Product Requirements Document (PRD)

**Document Version:** 1.0  
**Date:** November 2, 2026  
**Platform:** Android  
**Product Category:** Native Offline Music Player  
**Primary Experience:** Minimalist, premium, iOS-inspired  
**Target Library Size:** 50,000+ audio tracks  
**Development Approach:** Native Android, performance-first, modular architecture

---

# 1. Product Overview

## 1.1 Product Objective

AUREL is a native Android music player designed around five principles:

1. **Clarity:** Every screen has a clear purpose. No unnecessary controls, cards, labels or decorative elements.
2. **Fluidity:** Scrolling, navigation, transitions and playback controls respond immediately.
3. **Consistency:** Typography, spacing, iconography, colors, shapes and interaction patterns remain consistent throughout the application.
4. **Reliability:** Playback, indexing, library management and background operation must remain stable under real-world conditions.
5. **Craftsmanship:** Every interaction, including loading, empty states, dialogs, error states and tiny animations, receives deliberate design attention.

## 1.2 Target Audience

- People with large offline music collections.
- Users who prefer owning and managing local music.
- Audiophiles who use lossless audio formats.
- Users who appreciate minimal, premium interfaces.
- Users who want a reliable music player without advertisements or unnecessary features.

## 1.3 Product Scope

AUREL is an offline-first music player.

**Included:**
- Local audio discovery and playback.
- Music library management.
- Home dashboard.
- Songs, albums and artists.
- Search and filters.
- Now Playing experience.
- Queue management.
- Playlists and favorites.
- Sleep timer.
- Lyrics display.
- Audio equalizer.
- Light, dark and system themes.
- GitHub Releases-based application updates.
- Background playback.
- Android notification and lock-screen controls.

**Excluded from initial release:**
- Music streaming subscriptions.
- Social feeds.
- User accounts.
- Cloud synchronization.
- Advertising.
- Unnecessary AI recommendations.
- Online music discovery.

# 2. Technology Stack

Use native Android technologies. Do not build the application as a WebView or hybrid application.

| Layer | Technology |
|---|---|
| Language | Kotlin |
| UI | Jetpack Compose |
| Design foundation | Material 3, heavily customized |
| Architecture | Clean Architecture + MVVM |
| Playback | AndroidX Media3 / ExoPlayer |
| Background playback | MediaSessionService |
| Database | Room |
| Dependency injection | Hilt |
| Async operations | Kotlin Coroutines + Flow |
| Preferences | DataStore |
| Artwork loading | Coil |
| Networking | Retrofit + OkHttp |
| Background jobs | WorkManager |
| Navigation | Navigation Compose |
| Testing | JUnit, MockK, Compose UI Test |
| Performance testing | Macrobenchmark, Baseline Profiles |
| Updates | GitHub Releases API |
| Logging | Structured, release-safe logging |

### Architectural requirements

Implement the following layers:

- Presentation Layer
- Domain Layer
- Data Layer
- Playback Layer
- Platform Integration Layer
- Update Management Layer

The audio engine must be independent of the Compose UI.

**Critical architecture rule:** The UI must communicate with the playback engine through a MediaController/repository abstraction. Composable screens must never own the actual player lifecycle.

Room is the source of truth for indexed library metadata, playlists, favorites and playback history. Actual audio files must remain in their original storage locations.

# 6. Now Playing Screen

## 6.1 Design Philosophy

This is the most important screen in AUREL.

It must feel immersive, balanced, premium and immediately understandable.

Avoid the typical music-player mistake of adding every possible control to one screen.

### Layout hierarchy

1. Top navigation and playback context.
2. Large album artwork.
3. Track title and artist.
4. Playback progress.
5. Primary transport controls.
6. Secondary playback controls.
7. Next-up preview.

### Artwork

- Large square album artwork.
- Maintain original aspect ratio through appropriate cropping.
- Rounded corners with consistent continuous-feeling curves.
- No unnecessary borders.
- Subtle artwork transition when changing songs.
- Optional dynamic background derived from album artwork.

### Dynamic Artwork Background

Extract a representative color palette from artwork.

Use:
- A subtle dominant-color background.
- Carefully controlled gradients.
- Darkened or lightened supporting surfaces.
- High-contrast text.
- Minimal blur.

Do not allow the artwork to reduce text readability.

The proposed 14.7:1 contrast target should be treated as a visual reference, not a fixed requirement for every image. Enforce WCAG AA contrast at minimum for normal text and use stronger contrast wherever practical.

Never place white text directly over arbitrary bright artwork without checking contrast.

### Track Information

Display:
- Song title.
- Artist name.
- Favorite button.

Long-title behavior:
- Show the complete title.
- If it exceeds available width, perform one controlled marquee pass.
- Stop at the beginning.
- Never loop indefinitely.
- Provide an accessible full-title description.

### Playback Scrubber

Visual requirements:
- Thin resting progress line, approximately 4dp.
- Touch target at least 44dp high.
- Expanded visual thickness while dragging.
- Clear buffered-progress indication when available.
- Accurate seeking.
- Smooth progress updates without unnecessary recomposition.

Display:
- Elapsed time.
- Remaining time, such as `-1:48`.

Remaining-time display is the default presentation. Do not make the duration impossible to access when needed.

### Main Playback Controls

Primary controls:
- Previous.
- Play/Pause.
- Next.

Design:
- Large, prominent play/pause control.
- Target approximately 72dp for the primary visual control.
- Secondary skip controls smaller.
- Accent color reserved for the primary action.
- Immediate touch feedback.

Playback controls must support:
- Single taps.
- Rapid repeated taps.
- Previous/next queue boundaries.
- Seeking during buffering.
- Audio focus interruptions.

### Secondary Controls

Show no more than five visible options:

1. Shuffle.
2. Repeat.
3. Queue / Up Next.
4. Sleep Timer.
5. More.

The More menu contains:
- Lyrics.
- Equalizer.
- Add to Playlist.
- Go to Album.
- Go to Artist.
- Audio Information.
- Share, if supported.
- Other relevant actions.

Do not clutter the main player with secondary actions.

### Up Next

Show a compact preview of the next track.

Include:
- Artwork.
- Title.
- Artist.

Tapping opens the queue.

Queue management:
- Reorder tracks.
- Remove tracks.
- Clear queue with confirmation.
- Add tracks.
- Play a selected track.
- Handle queue exhaustion.
- Preserve queue state across configuration changes and process recovery where feasible.

# 13. GitHub Releases Update System

Use GitHub Releases as the distribution and update source.

### Update Flow

1. User opens Updates.
2. App checks the configured GitHub Releases endpoint.
3. Retrieve the latest stable release.
4. Compare release version with installed version.
5. Show an update dialog when a newer compatible version exists.
6. Display version, release notes and file size.
7. User selects Download.
8. Download APK with progress feedback.
9. Verify APK integrity and signing identity.
10. Launch Android's package installation flow.
11. User confirms installation.
12. Application restarts with the updated version.

### Update Interface

Dialog example:

**A new version is available**

Version 1.2.0

- Improved library scanning.
- Refined playback controls.
- Performance improvements.

Actions:
- Later.
- View Release Notes.
- Update Now.

### Security Requirements

- HTTPS only.
- Validate release metadata.
- Verify SHA-256 checksum.
- Verify APK signing certificate against the trusted release signer.
- Reject unexpected signing identities.
- Handle download interruptions.
- Handle insufficient storage.
- Handle unavailable GitHub services.
- Never install arbitrary APK files.
- Never attempt silent installation without authorized system privileges.

**Important:** GitHub Releases does not provide silent OTA installation for ordinary Android apps. The user must approve installation through Android's package installer, and the application may need permission to request package installation.

Do not describe this as a fully automatic background update system.

# 14. Audio Engine and Playback Requirements

This is a critical subsystem. A premium UI is worthless if playback is unreliable.

## 14.1 Supported Formats

Implement and test supported Media3/ExoPlayer formats, including where device decoders permit:

- MP3.
- AAC.
- FLAC.
- WAV.
- OGG Vorbis.
- Opus.
- M4A.
- ALAC, subject to decoder support.

Do not claim universal codec support across every Android device.

## 14.2 Lossless Playback

Requirements:
- Preserve source audio quality.
- Avoid unnecessary transcoding.
- Use supported device decoders.
- Support high-resolution source files where the device output path permits.
- Display source codec, sample rate, bit depth and bitrate when reliably available.
- Handle unsupported formats gracefully.

Distinguish lossless file decoding from bit-perfect output. Android's audio mixer, hardware and output route can resample or otherwise alter the output.

## 14.3 Background Playback

Implement:
- Foreground playback service.
- MediaSession.
- Media notification.
- Lock-screen controls.
- Bluetooth controls.
- Wired headphone controls.
- Audio focus handling.
- Audio becoming noisy handling.
- Playback restoration.

Playback must not depend on the UI Activity remaining alive.

## 14.4 Playback State Machine

Explicitly define states:

- Idle.
- Preparing.
- Buffering.
- Ready.
- Playing.
- Paused.
- Seeking.
- Ended.
- Error.

Prevent invalid state transitions.

Rapid play/pause/next/previous actions must not produce multiple conflicting player instances.

## 14.5 Queue Management

Support:
- Current track.
- Next track.
- Previous track.
- Shuffle order.
- Repeat off.
- Repeat one.
- Repeat all.
- Queue persistence.
- Queue restoration.
- Removed source files.
- Corrupted files.
- Unsupported files.

Use:
- Incremental indexing.
- MediaStore change detection.
- Stable track identifiers.
- Transactional database upserts.
- Stale record removal.
- Background processing.
- Scan cancellation.
- Scan progress reporting.

- Track ID.
- URI.
- Title.
- Artist.
- Album.

- Duration.
- Track number.
- Disc number.
- Year.
- File size.

Target 50,000+ tracks.

The system must:
- Avoid loading all songs into Compose state.

- Cache artwork thumbnails.

# 17. Motion and Interaction Design

Motion must communicate state, hierarchy and physical continuity.

It must never become decoration that slows down the experience.

## 17.1 Touch Feedback

- Respond on touch-down.
- Provide immediate visual acknowledgement.
- Use subtle scale or tonal changes.
- Avoid delayed press effects.
- Maintain correct ripple or pressed-state behavior.
- Support cancellation when the user moves away from a control.

Do not promise literally zero milliseconds of end-to-end response. The target is immediate perceptible feedback within the next rendered frame.

## 17.2 Spring Physics

Use interruptible spring-based animations for:
- Bottom sheets.
- Artwork transitions.
- Mini-player expansion.
- Queue interactions.
- Navigation surfaces.
- Press and release feedback.

Use damped harmonic motion:

`m × x'' + c × x' + k × x = 0`

Where:
- m = effective mass.
- c = damping coefficient.
- k = spring stiffness.

Tune stiffness and damping per interaction.

The animation must respond to a new gesture from its current position and velocity, not restart from the beginning.

## 17.3 Scroll Physics

Implement native Android scrolling behavior with carefully calibrated edge effects.

For an optional custom bounded overscroll model, use the proposed hyperbolic function:

`offset = (1 - 1 / (c × x / d + 1)) × d`

Where:
- x = pull distance.
- d = available screen dimension.
- c = tuning constant.

The curve should approach a bounded maximum without allowing infinite displacement.

However:
- Do not replace Android's native nested-scroll handling unnecessarily.
- Preserve accessibility and gesture navigation.
- Ensure horizontal and vertical scrolling do not conflict.
- Test on different screen densities and refresh rates.

The formula is a design hypothesis to calibrate, not proof of Apple's actual private UIKit implementation.

## 17.4 Motion Specifications

| Interaction | Target |
|---|---|
| Press feedback | Next rendered frame |
| Small control transition | 100–160ms |
| Screen transition | 180–280ms |
| Bottom sheet | 250–350ms |
| Artwork transition | 200–300ms |
| Spring settling | Physics-driven |
| Toast | Approximately 2–3 seconds |

Use motion preferences and accessibility settings appropriately.

## 17.5 Momentum and Scroll

- Use native fling physics.
- Avoid artificial scroll timers.
- Avoid resetting list positions unexpectedly.
- Preserve scroll state across navigation.
- Avoid nested scrolling unless necessary.
- Ensure high-refresh-rate devices remain smooth.

# 20. Performance and Reliability Requirements

The following are engineering targets, not guarantees.

| Metric | Target |
|---|---|
| Cold startup | p95 under 2 seconds on reference devices |
| Warm startup | p95 under 1 second |
| Cached library display | Under 500ms target |
| Search response | p95 under 200ms for indexed queries |
| UI frame budget | 16.7ms at 60Hz |
| High-refresh frame budget | 8.3ms at 120Hz |
| Main-thread blocking | No disk or metadata processing |
| Full-library indexing | Background and incremental |
| Playback control response | Immediate perceptible feedback |
| Playback state recovery | Defined and tested |
| Memory usage | Bounded with library size |
| Crash-free sessions | Target 99.9%+ after release stabilization |

Measure performance on actual devices rather than relying exclusively on emulators.

### Performance Rules

1. No database queries on the main thread.
2. No audio decoding on the UI thread.
3. No full-resolution artwork decoding for thumbnails.
4. No unbounded in-memory song collections.
5. No unnecessary recompositions.
6. No blocking operations inside Composables.
7. No repeated full-library scans.
8. No unnecessary Activity recreation.
9. No duplicate playback engine instances.
10. No expensive blur effects on large surfaces.
11. No unbounded coroutine launches.
12. No uncontrolled background work.

# 26. Final Product Design Rules

These rules apply to every screen, dialog, menu, popup, component and interaction.

1. Every element must justify its existence.
2. Prefer whitespace over decorative containers.
3. Use one consistent icon family.
4. Never use gradients without a clear functional or visual purpose.
5. Use artwork-derived color selectively.
6. Never sacrifice readability for aesthetics.
7. Never block playback while scanning music.
8. Never perform expensive operations on the main thread.
9. Never create duplicate player instances.
10. Never introduce layout shifts when content loads.
11. Never show skeleton loaders when cached content is already available.
12. Never animate every element independently.
13. Every animation must be interruptible where interaction requires it.
14. Every interactive element must provide immediate feedback.
15. Every empty state must explain what happened and what to do.
16. Every error must have a defined recovery path.
17. Every screen must respect Android system insets.
18. Every important operation must survive appropriate lifecycle events.
19. Every visual decision must be consistent with the design system.
20. No feature should be added merely because another music player has it.

# 27. Final Product Vision

AUREL should feel like a carefully engineered native music application rather than a generic Android music-player template.

The interface should be quiet. The playback should be dependable. The navigation should be predictable. The animations should feel physical. The typography should be precise. The library should scale without compromising performance.

**The defining characteristic of AUREL is not how many features it has. It is how little friction exists between opening the application and enjoying music.**

Build the audio engine and data architecture first. Build the visual experience on top of reliable foundations. Never hide an engineering limitation behind a beautiful animation.

**Product success criterion:** A user with 50,000 local music tracks should be able to open AUREL, find a specific song, start playback, navigate the library and continue listening in the background without experiencing avoidable friction.
